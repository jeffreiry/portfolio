# Sprocket App (Emily Backes) · Análise Rápida · 12/09/2026

**Referência:** https://emilybackes.design/case-study/sprocket-app

## 1. Seções e ordem
Hero → Case Study Summary → pesquisa (estatísticas do problema) → análise competitiva → mind map / arquitetura conceitual → user flow → processo de design (sketch → lofi → midfi → hifi) → galeria de telas finais (9 telas) → Challenges (reflexão crítica, incluindo viés de acessibilidade).

## 2. Métricas/resultados
- H1 já carrega o resultado: "How I doubled expected registration and app sign up in 3 months".
- Estatísticas de pesquisa (73%, 154.009, 80%) aparecem **cedo**, como prova do problema — não só no final como prova do resultado.
- Conclusão reafirma o número: "expected 1,500... received double that".

## 3. Incomum
- Progressão de fidelidade documentada lado a lado: sketch → lofi → midfi → hifi, como galeria sequencial (não só menção em texto).
- Seção final de "Challenges" admite viés de design/acessibilidade não resolvido — autocrítica real, não só "o que eu faria diferente" genérico.

## 4. O que eu roubaria
| Item | Impacto | Esforço |
|---|---|---|
| Estatísticas de pesquisa como prova do PROBLEMA, exibidas antes da solução | Alto | Baixo (é só reordenar/copy, se o dado já existir) |
| Progressão sketch→lofi→midfi→hifi como galeria visual sequencial | Alto | Médio (depende de ter os artefatos de baixa-fi guardados) |

## 5. Delta rápido
Meu portfólio tem metadados estruturados no hero que o Sprocket não tem, mas perde no uso de estatística de pesquisa como abertura de problema — meus cases (Enterprise AI, Shipping) mencionam discovery mas não citam números de contexto/mercado como justificativa do problema.
